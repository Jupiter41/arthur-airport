\begin{abstract}
Digital twins of complex cyber-physical systems are typically built as monolithic, closed-loop models that are difficult to extend and impossible to reproduce. We propose a layered fidelity architecture in which a digital twin begins as a pure event-driven simulation and progressively acquires physical, geospatial, and decisional capabilities - each phase building on the previous without architectural rewrites. To demonstrate this approach, we present Arthur International Airport (KART), a fully open-source, airport digital twin implemented using a specification-first development methodology with AI coding agent assistance. We show that structuring domain knowledge as machine-readable specification and skill files - readable by both human developers and large language model agents - reduces architectural errors and revision cycles in complex system development. The resulting system models flight operations, passenger flows, baggage handling, weather impacts, and hazardous incident cascades across seven microservices, with several layers such as LLM and a real-time geospatial interface. All artefacts, including specifications, skill files, and infrastructure code, are publicly available.

\keywords{Digital twins \and Airport operations \and Cyber-physical systems \and AI-assisted software engineering \and Specification-driven development \and Simulation architecture \and Progressive fidelity.}
\end{abstract}

\section{Introduction}

\begin{itemize}
  \item Context: airports are canonical cyber-physical systems; operational digital twins are typically monolithic, closed-loop models that are hard to extend and impossible to reproduce.
  \item Problem: fidelity expectations grow over a project's lifetime (logical operations $\rightarrow$ physical layout $\rightarrow$ real-world data $\rightarrow$ decision support); monolithic designs force an architectural rewrite at every step.
  \item \textbf{Research question.} How should digital twins of complex cyber-physical systems be architected so that fidelity can be acquired \emph{progressively} --- from pure event-driven simulation to physical, geospatial, and decisional layers --- without architectural rewrites, and can specification-first development with AI coding agents make such systems tractable for a single developer?
  \item Sub-questions: (RQ1) what layered architecture allows progressive fidelity acquisition; (RQ2) how do machine-readable specifications and skill files affect the correctness of LLM-agent-assisted implementation; (RQ3) what does a complete end-to-end implementation reveal about costs, benefits, and failure modes.
  \item Contributions: (i) a layered fidelity architecture; (ii) a specification-first methodology with skill files for AI coding agents; (iii) KART, a fully open-source airport digital twin ($\sim$44k LOC Python across nine services, $\sim$28k LOC React/TypeScript); (iv) honest lessons learned from fifty-plus sprints of agent-assisted development.
  \item Paper roadmap paragraph.
\end{itemize}

  \item Gap: no prior work combines a progressive-fidelity DT architecture with machine-readable specification artifacts designed to be consumed by both humans and LLM agents.

\section{Layered Fidelity Architecture}\label{sec:architecture}

\begin{itemize}
  \item Layer definitions:
    \begin{itemize}
      \item \textbf{L0 --- logical event-driven simulation}: domain state machines, Kafka event bus, graph-persisted state; no geometry, no external data.
      \item \textbf{L1 --- physical layer}: spatial layout (terminals, gates, runways, taxiways), distances, walking and taxi times.
      \item \textbf{L2 --- geospatial and real-world data layer}: map-based visualisation (Mapbox/Cesium), ADS-B flight overlay, live and historical METAR weather, BTS schedule calibration, OurAirports/OpenFlights reference data.
      \item \textbf{L3 --- decisional layer}: LightGBM queue forecasting, what-if and Monte-Carlo scenario analysis, DCF investment appraisal, autonomous operations with approval-gated commands.
    \end{itemize}
  \item Architectural invariants that make layers composable without rewrites: simulation-clock contract (no wall-clock reads), facts-only event bus, Neo4j as single source of truth, every state change emits an event.
  \item Capability ladder within each layer: visualisation $\rightarrow$ monitoring/alerting $\rightarrow$ prediction $\rightarrow$ prescription $\rightarrow$ actionability.
  \item Key property: each layer strictly consumes the contracts of the layer below; upgrading a layer never breaks lower ones (evidenced by the phased roadmap history landing without re-platforming).
\end{itemize}

\section{Specification-First Development with AI Agent Integration}\label{sec:methodology}

\begin{itemize}
  \item Write-before-code discipline: event-bus schemas, graph data model, simulation rules, and one specification per service precede any implementation; the spec is authoritative and deviations require updating the spec first.
  \item Skill-file format: concept explanation + copy-paste patterns + gotchas; cross-cutting skills (Neo4j/Cypher, Kafka producer/consumer, simulation clock, forecasting) plus one skill per service.
  \item Agent entry points (\texttt{CLAUDE.md}, \texttt{AGENTS.md}, editor rule files) route the agent to the relevant spec and skill before code is written.
  \item Hard rules as guardrails against known LLM failure modes: no wall-clock time in business logic, no service-to-service HTTP, no silent mutations, all data synthetic.
  \item Feedback loop: sprint post-mortems promote discovered gotchas back into skill files --- a living knowledge base shared by humans and agents.
\end{itemize}

\section{The KART Implementation}\label{sec:implementation}

\begin{itemize}
  \item Stack: nine FastAPI domain services, Node.js/Express API gateway, React/TypeScript dashboard suite; Kafka backbone; Neo4j graph store; Prometheus/Grafana/Loki/Jaeger observability; Kubernetes manifests and CI pipeline.
  \item Domain depth: nine-state flight lifecycle FSM with runway queueing and five-hop delay cascades; passenger flow with security congestion and a LightGBM model predicting queue depth 90 minutes ahead; thirty-zone baggage conveyor with dangerous-goods screening; four-state weather FSM generating ICAO-format METAR/TAF; rule-based incident cascade engine covering five hazard types.
  \item Scale: 420 daily movements, ${\sim}30{,}000$ passengers and ${\sim}36{,}000$ baggage items per simulated day; configurable clock up to $3600\times$ real time.
  \item Decisional layer realised in production code: financial service (P\&L, EU261 liability, carbon accounting), planning service (Monte-Carlo infrastructure scenarios, NPV/IRR investment appraisal on Eurocontrol Standard Inputs), analysis service (anomaly detection, slot-allocation MILP, autonomous mode with approval queue and per-domain command topics).
  \item Reproducibility: all specifications, skill files, infrastructure definitions, and data pipelines are open source; the airport itself is config-driven (a new airport is a YAML file, not code).
\end{itemize}

\section{Evaluation}\label{sec:evaluation}

\begin{itemize}
  \item Method: qualitative case study of a single-developer project across fifty-plus sprints, using the repository's documented revision history as the evidence trail.
  \item Engineering-quality metrics: 760+ unit tests including event-chain contract tests and consumer idempotency tests; staged CI (lint, unit, integration, Docker build, end-to-end smoke, load tests).
  \item Functional demonstrations: end-to-end cascade walkthrough (weather degradation $\rightarrow$ runway capacity drop $\rightarrow$ departure queue $\rightarrow$ gate conflicts $\rightarrow$ missed connections $\rightarrow$ EU261 exposure); counterfactual replay of past decisions; Monte-Carlo investment scenario comparing baseline vs.\ expanded infrastructure.
  \item Methodology evidence: single-source-of-truth tests introduced after refactors lock constants and schemas against drift between services --- the class of architectural error the skill files are designed to prevent.
  \item Honest scope: no controlled human study; all data is synthetic by design; quantitative claims are limited to system-level engineering metrics.
\end{itemize}

\section{Discussion}\label{sec:discussion}

\begin{itemize}
  \item What worked: contract-first discipline; config-driven airport identity (Open/Closed principle); promoting duplicated transport code into a shared library; hexagonal refactors that made domain logic unit-testable without containers.
  \item Iterating on the base: a mid-project architectural audit surfaced defects characteristic of fast agent-assisted development at scale (constants diverging between copies, recommendations displayed but never executed, ML endpoints reporting success without training). All were remediated through the same spec-first process --- evidence that the methodology self-corrects.
  \item Cautionary finding: without systematic review, such defects can pass unnoticed and even reach user-facing dashboards; audit and mutation-tested guards are a first-class part of the workflow, not an afterthought.
  \item Trustworthiness principle: delete or make real anything that advertises capability it lacks; predicted-vs-actual outcome measurement closes the learning loop.
  \item Generalisation: the layered-fidelity template and the spec/skill methodology transfer to other cyber-physical domains (ports, hospitals, warehouses).
  \item Threats to validity: single developer, single domain, self-reported revision-cycle claims, synthetic ground truth.
\end{itemize}

\section{Conclusion}

\begin{itemize}
  \item Answers: (RQ1) a four-layer architecture with strict upward-only dependencies supports progressive fidelity without rewrites; (RQ2) machine-readable specs and skill files measurably steer LLM agents toward architecturally consistent implementations; (RQ3) the complete implementation confirms feasibility while exposing the review practices needed to keep agent-generated systems trustworthy.
  \item Progressive fidelity plus specification-first agent development makes airport-scale digital twins tractable for a single developer; all artefacts are open.
  \item Future work: completing command-topic coverage across all domains, multi-agent reinforcement learning benchmarks using the twin as environment, and multi-airport network studies.
\end{itemize}
